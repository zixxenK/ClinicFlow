2. DETAILED DESIGN - GLOBAL CONCEPT

ClinicFlow is an administrative clinic-finding and appointment application. Patients can create an account, search for clinics, view availability, book, cancel, reschedule, and review upcoming appointments. Clinic staff with an active clinic membership can manage schedules and appointment outcomes. The interface is built with React, TypeScript, and Vite, and is packaged for Android and iOS through Capacitor. The project uses the five subsystems selected in Deliverable C: Patient Appointment Management, Clinic Finder, Database and Data Management, Accessibility Settings, and Notification System.

The application communicates with Supabase over HTTPS. Supabase Auth manages account registration, email verification, login, sessions, password recovery, and password changes. The frontend uses the signed-in user's session to make database requests. PostgreSQL stores clinic, staff, schedule, appointment, minimal booking-profile, waitlist, accessibility-preference, announcement, notification, and audit information. Row Level Security (RLS) limits access according to user identity and clinic membership. PostgreSQL functions check availability and validate booking, cancellation, rescheduling, check-in, and appointment-outcome operations. Database constraints reject overlapping active appointments.

Figure 1 shows the system boundary and the main information flow. Solid boxes and arrows represent implemented prototype behavior. Dashed boxes and arrows represent remaining work, including a hosted email provider and scheduled worker, SMS/push delivery, verified clinic listings, and native-device testing.

3. DETAILED DESIGN - SUBSYSTEMS

3.1 PATIENT APPOINTMENT MANAGEMENT

The Patient Appointment Management subsystem lets signed-in patients check availability, book, view, cancel, and reschedule appointments. Patients select a clinic and date. A PostgreSQL function combines clinic hours, staff hours, active clinic membership, existing appointments, schedule blocks, and the clinic time zone to return available slots. The default duration is 30 minutes; clinic administrators can set a duration from 15 to 120 minutes in 15-minute increments.

When a patient chooses a time, a PostgreSQL function checks the session and booking profile, confirms the clinic and time are still available, and inserts the appointment. The database prevents overlapping active bookings for both the staff member and patient. If another request takes the slot first, the function returns an error and the interface refreshes availability. While the page is open, availability, upcoming appointments, and the staff daily schedule refresh every 15 seconds. Cancellation and rescheduling also use database functions and create audit events. Clinic staff can view the daily schedule, update recurring hours, add unavailable periods, check patients in, cancel appointments, and mark completed or no-show outcomes, subject to active clinic membership and role.

The current prototype also supports waitlist joining and leaving. Cancelling a booking can create a one-hour offer for the next eligible waitlisted patient. The offer identifies the newly available time, but it does not reserve the slot; accepting it calls the standard booking function, which rechecks availability and can reject a competing booking. There is no staff-assisted patient booking workflow. Staff can edit multiple recurring intervals per weekday, including split shifts and closed days. A platform administrator can provision an existing verified Auth account for a clinic role; public signup cannot assign elevated access.

3.2 CLINIC FINDER

The Clinic Finder lets patients search active clinics by manually entering a city or Canadian postal code. Patients can set a maximum distance and filter by service, new-patient status, and appointment availability. The React interface sends these criteria to the PostgreSQL `search_clinics` function. The database resolves the entered location to a configured city or postal-prefix point, calculates approximate straight-line distance from clinic coordinates, applies filters, sorts by distance, and returns next availability. The interface displays clinic name, address, city, province, phone number, description, services, new-patient status, approximate distance, and next available time. Selecting a clinic passes its ID to appointment booking.

The app uses manually entered search text and does not request device location. The search input is used for the request but is not saved in application tables. Local clinic/provider data is synthetic and limited to Ottawa examples, the Ottawa city point, and postal prefixes K1N and K2G. No real verified listing has been imported, so this is not a verified or comprehensive directory. A local CSV import workflow requires HTTPS source details, source record ID/date, coordinates, a time zone, and a location within 25 km of uOttawa. The database excludes unverified records from search and displays synthetic listings as demos. Next availability is based on recurring clinic/staff hours, schedule blocks, and the clinic's configured appointment duration.

3.3 DATABASE AND DATA MANAGEMENT

Supabase Auth stores and verifies login credentials. After a user registers, a database trigger creates the matching application profile using the Auth user ID. A patient then completes a minimal booking profile containing their name and optional phone number. ClinicFlow does not store passwords, custom authentication tokens, date of birth, medical records, or clinical notes.

PostgreSQL stores profiles, minimal patient profiles, staff profiles, clinic memberships, clinic hours, staff hours, clinics, appointments, waitlist entries, notifications, announcements, accessibility preferences, schedule blocks, and audit logs. The patient profile stores a name and optional phone number; Supabase Auth stores account credentials. RLS limits patients to their own records and staff to active clinic memberships. Staff/administrator memberships must be assigned through a trusted administrative process and cannot be selected through public signup. The interface includes staff announcement publishing and patient waitlist management.

Availability and booking use PostgreSQL functions. Database constraints prevent overlapping active appointments. Appointment events and changes to patient profiles, clinic memberships, schedules, schedule blocks, announcements, waitlist entries, and accessibility preferences write audit records with actor, action, entity, and time. Narrow database functions also audit patient appointment-list reads, clinic schedule reads, and rejected booking attempts. Audit records do not store patient names, contact information, or booking request contents. Other reads and failed actions are not audited.

3.4 ACCESSIBILITY SETTINGS

The Accessibility Settings subsystem lets each signed-in user save English/French language preference, text size, high contrast, and text-to-speech settings. Text size and contrast are applied in the interface. Supported browsers use built-in speech synthesis to read appointment information without sending it to another service. The database stores each user's preferences and RLS restricts them to their owner.

The controls, preference storage, text-size styling, high-contrast styling, English/French labels, and speech behavior are implemented. Saved settings are loaded after sign-in and applied across the interface. Clinic and staff-entered information remains in its source language, and some database-generated errors may remain English. Screen-reader and physical-device testing remain incomplete.

3.5 NOTIFICATION SYSTEM

The Notification System creates generic in-app notices for bookings, cancellations, reschedules, and waitlist offers. Clinic announcements appear in the selected clinic's updates. Messages should remain generic and must not include health details; the prototype does not automatically detect sensitive text entered by staff.

Appointment database triggers insert generic in-app notification records and private email outbox jobs for confirmations, cancellation/reschedule updates, and eligible reminders scheduled 24 hours before an appointment. The outbox stores account and appointment identifiers, not email addresses or message bodies. RLS restricts each patient to their own in-app notices. The notification centre polls for new records every 15 seconds while the page is open, shows an unread count, and lets users mark items as read. While local development is running, a worker polls due email jobs every 10 seconds and captures them in Mailpit; the one-shot command is also available. A synthetic confirmation was captured in the local test. No production provider or scheduled background worker is configured; SMS and push are not implemented.

In-app notices appear while the user is signed in and the application is open. A local email job is delivered to Mailpit within about 10 seconds while npm run dev is running. If the hosted app is closed, the prototype does not yet run a scheduled worker to deliver a reminder. The one-minute target is not established for production or background delivery and must not be claimed as achieved.
